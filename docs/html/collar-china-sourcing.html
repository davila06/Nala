📡 Sourcing · RFQ · Fabricantes China

Collar GPS — ficha de sourcing y contacto a fabricantes

Basado en el estado real del código a 2026-08-24, no en el roadmap aspiracional. Define qué necesita soportar un fabricante en China y trae la plantilla de correo lista para enviar a los candidatos evaluados.

01 — Resumen ejecutivo
La ruta de menor esfuerzo ya existe en el código

Con lo implementado hoy, integrar un collar OEM chino como CollarProvider.Generic reutilizando el patrón de TractivePollingJob (polling REST cada 5 min) es la ruta más rápida — días, no meses. Este documento sirve para: (1) dejar claro qué debe soportar el proveedor técnicamente, (2) exponer los gaps de seguridad/backend a cerrar antes de aceptar tráfico real de dispositivos, y (3) traer el correo listo para los 4 fabricantes candidatos.

03 — Caminos de integración soportados
Polling (A) vs. Push directo (B)

🅰️ Polling REST — recomendado

Clonar ITractiveService → nuevo servicio del proveedor. ~1–2 días. Requiere que el proveedor tenga API REST para consultar posición por ID. Cero trabajo de firmware, cero problema de auth de dispositivo.

🅱️ Push directo HTTP

El endpoint ya existe, pero exige JWT de usuario hoy — no apto para miles de dispositivos. Falta tabla CollarDeviceCredentials + validación por API key. Solo viable si el proveedor permite firmware personalizado apuntando a servidor propio.

Paso a paso técnico del Camino A (idéntico al usado con Tractive)

  1. Autenticación con el proveedor. La mayoría de estas plataformas OEM usan usuario/contraseña de cuenta reseller o una API key estática (no OAuth2 como Tractive) — confirmar en el RFQ cuál modelo aplica, porque cambia si hace falta intercambio de token o basta con una key fija en Key Vault.
  2. Registro del dispositivo en la plataforma del proveedor. Cada collar trae un deviceId/IMEI de fábrica que debe asociarse a la cuenta de PawTrack antes de que la API devuelva datos — manual o vía API de aprovisionamiento del fabricante.
  3. Mapeo deviceId → Collar. El campo ExternalDeviceId de RegisterCollarCommand ya existe y se reutiliza sin cambio de esquema.
  4. Polling job dedicado. Servicio hermano a TractivePollingJob que filtra Collar.Provider == CollarProvider.Generic y consulta el endpoint de posición por cada deviceId activo.
  5. Normalización de la respuesta. Cada proveedor devuelve su propio formato de campos/unidades/timestamp — requiere mapeo a CollarPosition(Lat, Lng, BatteryPercent) para no filtrar el formato del proveedor al dominio.
  6. Errores y rate limits. Mismo patrón try/catch + LogWarning por collar sin abortar el batch; revisar si el proveedor limita requests/min — con 50+ collares puede requerirse un endpoint "bulk" en vez de una llamada por dispositivo.
  7. Persistencia de histórico. Reutiliza CollarLocation.Record(...) y el job de purga existente (>30 días) sin cambios.
  8. Validación end-to-end en staging. Registrar 1 collar físico de prueba y confirmar latencia movimiento→tab GPS (hasta 5 min, mismo comportamiento que Tractive).

Qué puede alargar el esfuerzo estimado de 1–2 días: falta de SDK/librería HTTP del proveedor (firmas HMAC manuales) o si su API exige suscripción previa a un webhook para "habilitar" el polling — ambos son preguntas explícitas del checklist de la sección 6.

Recomendación: arrancar con Camino A para el primer lote. Evaluar Camino B solo si se pasa a hardware 100% propio (CollarProvider.Own).

04 — Variantes de producto a cotizar en el mismo RFQ
Una familia de productos sobre una plataforma común

Pedir al mismo proveedor varios niveles de producto (no un solo SKU) da flexibilidad de pricing por segmento sin negociar con fabricantes distintos. El pedido piloto puede ser solo V1 — V2–V4 quedan como opciones de escalamiento.

Variante Qué incluye Impacto backend Impacto batería
V1 — GPS (base) Módulo GPS/LTE-M + GSM, sin extras Ninguno — ya soportado por CollarProvider.Generic Referencia base (~3–5 días con sleep)
V2 — GPS + cámara Foto periódica o bajo demanda Endpoint nuevo de ingesta + Blob Storage (no existe hoy) Alto — pedir consumo real por captura
V3 — GPS + pantalla e-ink Pantalla e-ink para batería/estado o QR estático Ninguno adicional si es solo informativa Bajo si es e-ink (~0 mA en reposo) — rechazar OLED
V4 — GPS + cámara + pantalla Combo completo ("flagship") Suma de V2 + V3 El más alto — requiere validación con muestra real

Por qué pedir las 4 en el mismo correo: compara el costo incremental real de cada componente sobre la misma base de GPS, con datos de precio/consumo en vez de estimaciones.

06 — Checklist de confirmación por proveedor
Qué preguntar antes de decidir
  • ¿API REST o protocolo binario propietario (GT06/JT808)?
  • ¿Webhook/push a servidor propio, o solo polling contra su nube?
  • ¿Cuáles variantes V1–V4 (GPS, GPS+cámara, GPS+pantalla, combo) pueden fabricar sobre la misma plataforma?
  • Para V2 (cámara): ¿resolución, formato, tamaño de archivo, frecuencia máxima de captura sostenible?
  • Para V3 (pantalla): ¿tamaño/tipo e-ink disponible, consumo en reposo/refresco, contenido fijo o actualizable?
  • ¿Consumo de batería estimado por variante, bajo un escenario de uso concreto?
  • ¿Certificaciones vigentes (FCC/CE/ROHS) y bandas LTE-M/NB-IoT compatibles con CR?
  • ¿MOQ real y precio FCA Shenzhen a 50/100/500 unidades, por cada variante?
  • ¿Costo y tiempo de 2–3 muestras por variante antes de confirmar orden?
  • ¿Firmware personalizable (marca propia, endpoint propio)?
  • ¿SIM/plan de datos IoT recomendado o eSIM ya activada?
  • ¿Lead time de producción y envío a Costa Rica?

08 — Roadmap backend al recibir specs
Pasos de implementación
  • Crear I{Proveedor}Service clonando la forma de ITractiveService.
  • Registrar el servicio en InfrastructureServiceCollectionExtensions.cs con HttpClientFactory dedicado.
  • Extender el polling job para incluir collares con Provider == CollarProvider.Generic.
  • Si se confirma V2 (cámara): diseñar endpoint de ingesta de imagen (POST /api/collars/pet/{petId}/photo) + almacenamiento en Blob Storage y política de retención.
  • Si se confirma V3 (pantalla): implementar CollarQrBindings + POST /api/collars/bind-serial solo si el contenido depende de un serial vinculado dinámicamente.
  • Solo si Camino B: crear CollarDeviceCredentials + cambiar el endpoint a [AllowAnonymous] con validación de API key.
